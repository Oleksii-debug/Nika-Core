# Дані Nika після оновлення

Nika використовує одну папку даних користувача. У Windows це папка `NikaCore` у локальних даних профілю, звичайно `%LOCALAPPDATA%\NikaCore`. Вона не залежить від папки запуску чи номера версії. Файли програми та база `nika_core.db` зберігаються окремо.

Перед оновленням закрийте всі копії Nika. Збережіть резервну копію старої папки даних разом із файлами `-wal` та `-shm`, якщо вони є. Для працюючої бази використовується штатна функція резервного копіювання SQLite; окреме копіювання лише файла `.db` під час роботи може пропустити недавні записи.

Під час першого запуску зібраної програми перевіряються два відомі старі місця: `data\nika_core.db` у папці запуску та поряд із виконуваним файлом. Якщо є рівно одна придатна стара база, а в новому місці немає користувацьких записів, Nika створює перевірені резервні копії та переносить дані штатним механізмом відновлення. Старий файл залишається на місці.

Завдання, учасники команд, розклад, дозволи та записи виконаних дій переносяться разом. Nika не запускає завдання повторно через сам факт перенесення. Запис про завершене перенесення міститься всередині нової бази: переривання процесу після відновлення не дозволяє повторно замінити нові дані старою копією.

Після успішного перенесення користуйтеся оновленою програмою. Якщо стара копія Nika згодом змінить стару базу, наступний запуск повідомить про конфлікт. Програма не об'єднує різні історії автоматично.

## Якщо з'явилося повідомлення про відновлення

Повідомлення відкривається у звичайному діалоговому вікні Windows до запуску завдань. Натисніть Enter, щоб його закрити. Закрийте інші копії Nika та збережіть обидві папки даних. Не видаляйте жодну базу, щоб прибрати повідомлення.

Причиною можуть бути дві різні старі бази, користувацькі записи вже в новій базі, змінена стара база після перенесення, пошкоджений файл або дані новішої несумісної версії. Потрібно визначити правильну історію та відновити її через штатний механізм резервної копії з перевіркою й підтвердженням. Автоматичне розв'язання такого конфлікту не виконується.

Старі бази в довільних інших папках не шукаються по всьому диску. Якщо попередній запуск використовував іншу папку, збережіть її для явного відновлення. Для технічного відновлення абсолютний `NIKA_DB_PATH` має пріоритет; сумісний `NIKA_DATABASE_PATH` залишається другим варіантом. Явний шлях вимикає автоматичний пошук старих баз. Відносні шляхи відхиляються.

## Перевірки та межі

Автоматичні перевірки охоплюють українські шляхи, відновлення після обриву, записи у WAL, повторний запуск, конфлікт баз, зміну старої бази, один власник запуску та запис іншого процесу перед заміною. Копіювання блокує цільову базу до перевірки її порожнього стану й утримує блокування до завершення операції.

Людська перевірка NVDA та повний сценарій оновлення кінцевого пакета мають окремі приймальні вимоги. Цей документ не оголошує їх виконаними.

Технічна основа: наявні `platformdirs`, Pydantic Settings, `SQLiteStore` та `SQLiteRecoveryManager`. Нової залежності чи іншого механізму запису завдань немає. Резервні копії початкової та підготовленої бази разом із контрольними сумами зберігаються у `legacy-adoption-backups` поряд із новою базою. Запис перенесення містить локальний шлях старої бази; звичайна подія аудиту містить ідентифікатор та відбиток, без вмісту даних.

Документація використаних механізмів: [SQLite backup у Python](https://docs.python.org/3/library/sqlite3.html#sqlite3.Connection.backup), [блокування SQLite](https://sqlite.org/pragma.html#pragma_locking_mode), [папки даних platformdirs](https://platformdirs.readthedocs.io/en/latest/api.html), [блокування файла Windows](https://docs.python.org/3/library/msvcrt.html#msvcrt.locking).

# Налаштування джерел команди у Windows

Це шлях для порівняння двох локальних джерел наявною командою з двох виконавців і перевіряльника. Налаштування зберігаються в даних Nika. Python і редагування змінних середовища користувачу не потрібні.

## Налаштування з клавіатури

1. Підготуйте два різні файли в одній папці. Підтримуються TXT, MD, HTML, CSV, JSON, PDF, DOCX та XLSX; кожен файл — до 16 МіБ.
2. У Nika натискайте Tab до посилання «Джерела команди», потім Enter. Перейдіть до поля «Папка джерел — повний шлях» і введіть повний шлях до папки без зовнішніх лапок.
3. У полях «Перший файл — назва в цій папці або повний шлях» і «Другий файл — назва в цій папці або повний шлях» введіть назви файлів або їхні повні шляхи.
4. Перейдіть до кнопки «Зберегти джерела» й натисніть Пробіл. У разі успіху програма повідомить про збереження та переведе фокус у поле «Що має зробити Nika?».
5. Введіть команду порівняння. Перейдіть до кнопки «Створити завдання» й натисніть Пробіл. Стан завдання, три учасники й підсумок доступні в розділі «Командне завдання».

Пробіли та українські символи у шляхах підтримуються. Посилання за межі вибраної папки, однакові файли, відсутні або непідтримувані файли відхиляються до створення завдання.

## Збереження та відновлення

- Налаштування залишаються після закриття і повторного запуску Nika.
- Новий вибір джерел застосовується до нових завдань. Уже прийняте завдання зберігає свою конфігурацію, навіть якщо воно ще стоїть у черзі.
- Два вікна не можуть непомітно перезаписати зміни одне одного. За конфлікту натисніть «Перечитати збережені», перевірте поля та повторіть збереження.
- Незбережене введення не повинно зникати через фонове оновлення стану.
- Пошкоджена або новіша несумісна конфігурація не підмінюється типовою. Завдання з попередньої версії не переприв'язуються до інших джерел.
- Завершена команда відновлює збережений результат без повторного запуску учасників.

Для розробників: `AppConfig` з `NIKA_V01_SOURCE_*` залишається початковим варіантом конфігурації, доки користувач не збереже вибір через інтерфейс. Збережена конфігурація має пріоритет. Вона та незмінні посилання завдань використовують окреме версійоване розширення тієї самої SQLite-бази; TaskQueue залишається єдиним власником запису завдань. Журнал містить подію та версію, без шляхів і вмісту файлів.

## Межі цього етапу

Цей сценарій не підтверджує готовність довгого вебмоніторингу, пакетної обробки двадцяти сайтів, вибору мовної моделі, усіх наступних версій або всього Full Product Vision. Ці можливості мають окремі приймальні вимоги.

Автоматична Windows-перевірка заповнює справжні елементи зібраної програми через UI Automation, зберігає контрольовані джерела, запускає завдання та очікує видимий завершений результат. Людська перевірка доступності залишається окремою.

## Зміни і повернення до попереднього коду

Додано налаштування джерел, захищене збереження та незмінні прив'язки прийнятих завдань. Існуючий runtime, TaskQueue, скасування та браузерні адаптери збережені.

Інтерфейс узгоджено з фактичним складом команди: два незалежні виконавці та перевіряльник. Підтримано також попередній склад ролей; повторний ідентифікатор учасника або неповний склад не видається за завершену команду. Відображення перевіряється на результаті реального запуску через той самий міст, яким користується зібрана програма.

Перед звичайним оновленням діє штатна процедура резервного копіювання даних. Попередній інтегрований код збережений у Git. Не повертайте старішу версію на нові дані для продовження незавершених завдань: стара версія не знає нових прив'язок джерел. Для повернення використовуйте відповідну резервну копію та узгоджений із нею пакет.
